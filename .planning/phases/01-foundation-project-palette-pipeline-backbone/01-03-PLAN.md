<objective>
Migrate the §3 data model from series-scope to project-scope, add the page stage column
the pipeline registry needs, and make persistence durable and portable.

This is D-01 and D-02 in full: `Series` becomes `Project`; `palette_entry` and `entity`
re-point from `volume_id` to `project_id`; `volume.palette_revision` moves onto the
project row. CONTEXT.md is explicit that this is a schema migration of
`entities.py` + `store.py` + `tests/test_store.py`, not a rename.

It also closes the user's resolution of RESEARCH.md Open Question 1: WAL journal mode
plus a mandatory explicit checkpoint, because without the checkpoint D-04's "copy the
folder and it works" promise is not actually kept.

Purpose: every other backend plan in this phase calls `Store`. Finishing the whole
`Store` surface here — including the methods plans 01-06 through 01-09 need — is what
lets those plans run in parallel without fighting over one file.

Output: a migrated `entities.py`, a complete `store.py`, updated public exports, and a
green `tests/test_store.py`.

**No data migration script is needed.** RESEARCH.md § Runtime State Inventory verified
this is a pre-release codebase: no artist has ever created a `project.db` under the
current schema, and `tests/test_store.py` builds a fresh database per test in `tmp_path`.
Edit the schema in place.
</objective>

In `Store.__init__`, after `sqlite3.connect` and before `executescript(SCHEMA)`, execute
`PRAGMA journal_mode=WAL;` and `PRAGMA busy_timeout=5000;`. WAL is the user's resolution
of RESEARCH.md Open Question 1 and is what makes plan 01-06's per-request connections safe
under a read-during-write; the busy timeout is what stops a GET landing mid-POST from
raising `sqlite3.OperationalError: database is locked`.

Add `def checkpoint(self) -> None:` executing `PRAGMA wal_checkpoint(TRUNCATE);`. Its
docstring must state plainly why it exists: WAL keeps recently committed data in
`project.db-wal`, and D-04 promises the artist can copy, move or hand over the project
folder and have it work — truncating the WAL back into `project.db` is what actually keeps
that promise. Cite RESEARCH.md Pitfall 1 and the resolved Open Question.

Call `self.checkpoint()` from `close()` before `self.conn.close()`, so the context-manager
exit path already leaves the folder in a copyable state. Plan 01-06's explicit
`POST /api/projects/close` route calls `checkpoint()` too — belt and braces, because the
per-request `Store` in Pattern 1 opens and closes on every request and the artist's
"I'm done, I'm going to zip this folder" moment is a distinct user action.

Do **not** batch, defer, or wrap writes in a longer transaction anywhere. Every existing
`Store` method already commits synchronously before returning; PROJ-05's "a refresh or
crash loses no work" is satisfied by that discipline and would be broken by adding a
write-behind cache. State this in the `checkpoint` docstring or the class docstring so a
later phase does not "optimise" it away.
