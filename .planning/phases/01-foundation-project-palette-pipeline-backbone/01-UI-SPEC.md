# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** No frontend exists yet — this is a greenfield build (confirmed: no `package.json`, `components.json`, or `src/**/*.ts` anywhere in the repo). This document is the contract for the entire app shell, not just Phase 1's screens, because CONTEXT.md is explicit that the shell "must be able to host [a full-bleed canvas editor] without being redesigned" when Phases 2, 3 and 6 add one. Tokens, chrome and layout rules declared here are meant to survive unchanged through Phase 7.

**Governing constraint (read before anything else):** The artist is a professional colourist who lives in Photoshop/Clip Studio Paint all day and judges colour by eye against their own artwork and palette swatches inside this app. A tinted or high-chroma chrome around that artwork or those swatches actively misleads colour judgement — this is a functional defect, not a taste preference. Every colour token below is true neutral (R=G=B, zero hue, zero saturation) except the two deliberately reserved accent/destructive hues, which are kept low-chroma and never placed adjacent to swatches or artwork without a neutral gutter.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — no shadcn. Rationale below. |
| Preset | not applicable |
| Component library | none (hand-rolled component set over plain CSS custom properties) |
| Icon library | Lucide, static SVG, self-hosted (MIT, no CDN dependency — this app runs offline on one machine) |
| Font | Inter (self-hosted variable woff2), fallback `system-ui, -apple-system, sans-serif` |

**Why no shadcn (discretion call, per CONTEXT.md "Claude's Discretion"):** shadcn's component model is React-first (or React-port-first for Svelte/Vue). CONTEXT.md and STACK.md lock in a vanilla-TS + Konva approach for the canvas editors specifically *because* a reactive framework's render model fights imperative drag/freehand-stroke interaction — and explicitly warn not to put the canvas editors inside one when they arrive in Phase 2/3. Introducing shadcn now would mean either (a) picking React for the shell only, creating two different UI paradigms in one app with a seam at the canvas boundary, or (b) forcing shadcn onto a framework it wasn't built for. Neither is worth it for a shell that is three screens (project picker, volume/page grid, palette manager). Plain CSS custom properties as design tokens, consumed by both the vanilla-TS shell and the vanilla-TS/Konva editors, keep one styling vocabulary across the whole app and cost nothing to carry into Phase 2/3.

**CSS approach:** Plain CSS with `:root` custom properties for every token in this document (`--color-surface-dominant`, `--space-md`, `--font-size-body`, etc.). One `.css` file colocated per component/screen. No Tailwind, no CSS-in-JS, no preprocessor — nothing here needs it, and it keeps parity between the shell and the future canvas editor's own styling.

**Registry safety gate:** not applicable (no shadcn, no registries).

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, inline padding inside chips/badges |
| sm | 8px | Compact spacing: swatch card internal padding, form field gaps |
| md | 16px | Default element spacing: between form fields, list row padding |
| lg | 24px | Section padding: sidebar sections, panel/card padding |
| xl | 32px | Layout gaps: gutters between major regions (sidebar/content) |
| 2xl | 48px | Major section breaks: page header to page body |
| 3xl | 64px | Page-level spacing: empty-state vertical centring offset |

**Exceptions:**
- Icon-only interactive controls (accept/reject on a proposal card, delete-× on a palette swatch, kebab menu) are **32px** square hit targets, not the usual 44px touch-target minimum. Justification: this is a desktop, mouse-and-stylus-driven professional tool (per PROJECT.md constraints — single machine, local GPU, no tablet/touch target), not a touch-primary surface. 32px matches the 8-point scale and is comfortable for cursor/stylus precision.
- Top toolbar strip (page header, stage-indicator row) is a fixed **56px** height — not itself a spacing token, but declared here because Phase 2/3's canvas editor toolbar reuses this exact height so the chrome doesn't jump between phases.
- Palette swatch card is a fixed **120×120px** cell (96px colour swatch + 24px label strip) — chosen as a multiple of 8, sized for comfortable colour comparison against reference art without crowding the grid.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 (regular) | 1.5 |
| Label | 12px | 600 (semibold) | 1.4 |
| Heading | 18px | 600 (semibold) | 1.2 |
| Display | 24px | 600 (semibold) | 1.2 |

Exactly two weights in use: 400 and 600. No italics, no additional weights.

- **Body** — palette entry names, page/volume list rows, form inputs, dialog copy.
- **Label** — stage-strip segment names, section headers inside the sidebar ("Volumes", "Palette"), form field labels, status pills. Rendered with slight letter-spacing (0.02em) since it doubles as small-caps-style metadata text.
- **Heading** — screen titles ("Palette", volume name, page name).
- **Display** — project name in the top toolbar / project picker.

This is deliberately dense, information-forward typography (14px body, not 16px) — the audience is a professional working in Photoshop/CSP all day, not a marketing-site visitor; the app should read like adjacent professional tooling, not a consumer dashboard.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#1E1E1E` | App background, main content canvas surround |
| Secondary (30%) | `#2B2B2B` | Sidebar, cards, page/palette grid rows, toolbar strip, modals |
| Accent (10%) | `#5B8DEF` | See reserved-for list below — nothing else |
| Destructive | `#D9534F` | Destructive actions only — see reserved-for list below |

Supporting neutrals (not part of the 60/30/10 split, declared for completeness since every text/border token must also stay true-neutral):

| Token | Value | Usage |
|-------|-------|-------|
| Border/divider | `#3D3D3D` | Card borders, list dividers, input borders |
| Text primary | `#E8E8E8` | Body/heading/display text |
| Text muted | `#9A9A9A` | Label text, placeholder text, secondary metadata (timestamps, stage names not yet reached) |

**Why dark neutral, not light:** matches the convention professional colour tools already use (Photoshop, Clip Studio Paint, and colour-grading suites default to a neutral dark surround) specifically because a neutral gray point next to artwork and palette swatches is what keeps the artist's eye from making a false white-balance judgement. Every dominant/secondary/border/text token above is true neutral (R=G=B) — verify this holds for any token added later; a single warm- or cool-tinted gray defeats the entire point.

**Accent reserved for** (explicit list — nothing else may use this colour):
- Primary CTA buttons: "Create Project", "Upload Pages", "Confirm & Continue to {stage}", "Accept" on a character-sheet proposal, "+ Add Colour"
- The current/selected item indicator: selected page row, selected palette entry, selected volume in the sidebar tree
- The current-stage marker in the 8-segment pipeline strip

**Destructive reserved for**:
- Delete controls: delete palette entry, delete page, delete volume, delete project
- The "Go back to an earlier stage" entry point and its confirming button
- "Reject" on a character-sheet proposal (a lighter-weight destructive use — see Copywriting contract; rejecting a proposal is cheap, unlike Go-Back, but it is still a discard action and gets the destructive hue, not accent)

No other element may use accent or destructive colour. Icons default to text-muted or text-primary; only interactive, accent-reserved or destructive-reserved elements deviate.

## Phase-Specific Interaction Contracts

These patterns are called out explicitly because CONTEXT.md flags them as needing "a real contract, not a generic pattern." Planner and executor should treat this section as load-bearing, equal in weight to the token tables above.

### 1. Pipeline stage indicator (PROJ-04, D-06/D-07/D-11)

Every page displays the full 8-stage chain as a horizontal segmented strip: **Import → Panels → Protected → Zones → Propose → Snap → Review → Export**. This is true in both the page grid (compact strip, 4px-tall segments under each page thumbnail/row) and the page detail header (full strip, 24px tall, with stage names in Label typography beneath each segment).

Per-segment visual states (Phase 1 implements only the first two states below; the rest are declared here so Phase 2+ reuses the same component without redesign):
- **Completed/locked** — filled with accent colour, small checkmark glyph. Not clickable except via the Go-Back entry point (below).
- **Current** — outlined in accent colour, filled with secondary surface colour, Label text in text-primary (not muted).
- **Not yet reached, reachable in a future phase** — filled with the border/divider neutral (`#3D3D3D`), Label text in text-muted, not clickable, tooltip on hover reads "Available in a later phase."
- **Not yet reached, no runner exists this phase** — Phase 1 has no way to distinguish this from the state above (only Import has a runner) and must not try to — the artist should never see an internal "not implemented" distinction. Both render identically as the neutral "not yet reached" segment.

Phase 1 reality: every page's strip shows Import as Completed and all seven remaining segments as the neutral not-yet-reached state. There is no confirm step visible for Import specifically — a successful upload auto-advances the page to Import-complete, since there is nothing yet for the artist to review at that boundary (review only becomes meaningful once Panels exists in Phase 2).

### 2. Confirmation gate (D-06, D-07 — the reusable pattern, exercised fully starting Phase 2)

When a stage's runner produces output for a page, that stage's dedicated review surface (built in the phase that owns it) ends in a persistent action area with exactly one primary control:

- **"Confirm & Continue to {next stage name}"** — accent-coloured, names the concrete next stage every time, never a bare "Confirm" or "Next".
- No explicit reject control exists at this gate — the artist simply keeps editing until satisfied; confirming is the only forward action.
- On confirm, the stage's segment transitions Current → Completed (checkmark, accent fill) and that stage's data becomes read-only in its normal editing surface — further edits require the Go-Back flow below.

### 3. Destructive "Go back" contract (D-08 — the one the user was emphatic about)

This is the standing destructive-confirmation pattern for the whole project — every irreversible or costly action (delete project/volume/page/palette entry, and Go-Back specifically) uses this shape, not a generic browser-style "Are you sure?".

- **Entry point:** a low-emphasis, destructive-coloured text link — "Go back to an earlier stage" — positioned near the stage strip, never a filled button and never visually competitive with the "Confirm & Continue" primary action. This is deliberate: forward movement should be the path of least resistance, backward movement should require a conscious reach.
- **Target selection:** artist picks one earlier (already-completed) stage from a list.
- **Confirmation dialog** (modal, secondary surface, centred):
  - Heading: **"Go back to {stage name}?"** — never "Are you sure?"
  - Body: a sentence computed from real data at the moment the dialog opens, e.g. *"This discards zone edits on 6 panels and re-runs colour proposal for the whole page."* This sentence is generated server-side from the actual stages and counts being invalidated — it must never be a static template string with no numbers in it. If the planner cannot yet compute the affected-count for a given stage transition (true for Phase 1, since only Import exists), the dialog is simply not reachable yet — do not ship a version that shows a vague sentence instead of a computed one.
  - Confirm button: destructive-coloured, labelled with the concrete verb and cost — **"Go back and discard {N} edit{s}"** — never "Yes" or "OK".
  - Cancel button: **"Stay on {current stage name}"** — not a bare "Cancel", so the artist reads what staying means too.
- Phase 1 does not need a working instance of this dialog (no stage past Import exists to go back from), but the component and copy contract above is what Phase 2 onward must implement without re-deriving it.

### 4. Palette extraction recovery (D-15, PAL-01/PAL-03)

Adaptive extraction means the app sometimes returns the wrong count of colours. The recovery path must live on the same screen as the result, not a separate palette page:

- After a swatch upload finishes, the artist lands directly on the palette grid, pre-populated with the newly extracted entries as swatch cards (colour swatch + auto-name "Colour 1".."Colour N", inline-editable name).
- Two controls are present on this same view at all times, extraction or not: **"+ Add Colour"** (accent, opens a colour picker, adds a new card into the grid immediately) and a **× delete** control on every card, including ones just extracted seconds ago.
- There is no separate "review extraction" screen distinct from "the palette" — they are the same view. This is what satisfies D-15's requirement that manual add/delete be reachable directly from the extraction result.

### 5. Character-sheet proposal accept/reject (D-05, PAL-02)

- Upload is a bare drag-and-drop with zero prompts (per D-05 — no naming, no metadata asked at upload time).
- Result renders as a grid of proposal cards (visually distinct from confirmed palette cards — proposal cards get a dashed border in the border-neutral colour, not a solid one), each with per-card Accept (accent, check icon) and Reject (destructive, × icon) controls, plus a checkbox for multi-select.
- **Reject** needs no confirmation dialog — proposals aren't real data yet, discarding one is cheap and reversible (re-upload the sheet). This deliberately does NOT use the Go-Back destructive-dialog pattern; that pattern is reserved for actions with real cost.
- **Accept** (single or multi-select-then-accept-as-one-action) triggers a lightweight inline prompt, not a full-page navigation: for each accepted entry, two fields — "Character name" (shared across the batch if multiple entries accepted together, editable per-entry if they belong to different characters) and "Part" (per-entry: hair, base, eyes, etc.). Submitting writes each entry as "{character} / {part}" and moves the card from the proposal grid into the real palette grid.

### 6. Palette recolour live-update feedback (PAL-04, D-09)

The server side of this already exists (`update_palette_rgb` + `panels_affected_by`) — the UI's job is purely feedback, not data flow:

- Colour-picker commits on close/blur (not every drag frame) to avoid flooding writes, but the swatch card itself updates live during drag for direct visual feedback.
- On commit, a small non-blocking toast appears — **"Updated on {N} page{s}."** — bottom-of-viewport, auto-dismisses after ~3s, no button, no modal.
- This is explicitly NOT the Go-Back destructive pattern — no confirmation, no dialog, no stage-strip change anywhere, because D-09 makes palette edits sit entirely outside the stage chain. Any visible page thumbnail must refresh to reflect the new colour without a manual reload (thumbnails themselves don't exist until later phases render flatted previews — this rule is declared now so it isn't re-litigated then).

### 7. Persistence / autosave feedback (PROJ-05)

There is no Save button anywhere in this app.

- Every discrete edit (rename, recolour commit, add/delete entry, page upload complete, project/volume create) fires immediately on the action that produces it (blur, click, drop) and the UI reflects the new state as its own confirmation — no "Saved ✓" toast for routine edits, that would be noise on every keystroke.
- The one exception: operations with real latency (page/character-sheet upload, swatch extraction) show a determinate progress bar with percentage in the secondary surface colour, accent-filled.
- On failure only: a persistent (not auto-dismissing) inline error banner appears at the point of the failed edit, worded per the Copywriting contract's Error state row. The artist's typed/attempted value must remain visible and editable in place — never silently cleared or reverted.

### 8. Screen inventory and shell layout (must host a future canvas editor unchanged)

- **App shell:** persistent left sidebar (secondary surface colour, 240px fixed width) — project name/switcher at top, a collapsible Volume → Page tree below it, a "Palette" entry point pinned beneath the tree.
- **Top toolbar strip:** 56px fixed height, secondary surface colour, spans the main content area's full width. Phase 1 shows breadcrumb/title + the stage strip (when a page is open). Phase 2/3 reuse this exact strip for the canvas editor's tool controls (select/draw/merge/split modes) — do not add per-screen custom-height headers that would need to be reconciled with this later.
- **Main content area:** full-bleed, no card padding, dominant surface colour, occupying all space right of the sidebar and below the toolbar. Phase 1 fills it with forms/lists (project picker, volume/page grid, palette grid). Phase 2/3 mount the Konva canvas edge-to-edge into this exact same region — this is the constraint that rules out a padded "dashboard card" content layout now, since retrofitting one later would mean re-laying out the shell.
- **Screens this phase builds:** Project picker/recent-projects list (D-04's folder-pick model) → Project shell (sidebar + empty content) → Volume/Page grid (per volume) → Page detail (stage strip + upload state, no editor yet) → Palette grid (extraction result + hand edits, doubles as the character-sheet proposal review surface).
