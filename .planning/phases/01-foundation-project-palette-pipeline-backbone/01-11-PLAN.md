<objective>
Build the app shell and the project picker: the typed API client every view uses, the hash
router, the sidebar/toolbar/content layout, and the screen an artist actually starts on.

Purpose: 01-UI-SPEC.md §8 is explicit that the shell "must be able to host a full-bleed canvas
editor without being redesigned" when Phases 2, 3 and 6 add one. That constraint is what rules
out a padded dashboard-card content layout now, since retrofitting one later would mean
re-laying out the shell. Getting the three-region grid and the token vocabulary right here is
cheaper than doing it twice.

This plan also owns the shared contracts for the two frontend plans that follow: the API
client, the router's route table, the stub view modules and the toast component all land here,
so plans 01-12 and 01-13 each fill their own view files without either of them touching
`main.ts`, `router.ts` or `client.ts`.

Output: a running app shell served by `vite dev` against `comiccolor serve`, with a working
project picker.

**No component framework.** 01-UI-SPEC.md's Design System table settles it: "none —
hand-rolled component set over plain CSS custom properties", and RESEARCH.md § Anti-Patterns
records that this supersedes STACK.md's "introduce Svelte if the shell grows" fallback. Views
are functions that build DOM and return a teardown; state is plain module-scope objects.
</objective>

`frontend/src/api/client.ts`:
  - `apiUrl(path: string, query?: Record<string, string | number | undefined>): string` —
    builds a **relative** `/api/...` URL with encoded query parameters, skipping undefined
    values. Relative because `vite dev` proxies `/api` and production serves the SPA from the
    same FastAPI process; a configurable base URL would be dead weight and a way to
    accidentally point the app at another machine.
  - `class ApiError extends Error` with `status: number` and `detail: string`, plus a static
    `fromResponse(res: Response): Promise<ApiError>` that reads FastAPI's `{"detail": ...}`
    body, handles the 422 validation-error array shape, and falls back to a status-derived
    sentence that still names what failed. The backend already ships UI-SPEC-shaped copy in
    `detail` for every deliberate error (plans 01-07 through 01-10 define the constants), so
    views render `error.detail` directly rather than inventing their own wording — that is how
    the Copywriting Contract stays in one place instead of drifting across five views.
  - A private `request<T>()` helper: `fetch`, throw `ApiError` on a non-ok response, return
    `undefined` for 204, otherwise parse JSON.
  - An `api` object grouping typed functions for every route the phase exposes:
    `projects.create/open/close/current/recent/browse`,
    `volumes.list/create/rename/remove`,
    `pages.upload/list/get/remove/imageUrl`,
    `pipeline.stages`,
    `palette.list/create/update/remove/swatch`,
    `references.uploadSheet/accept/discard/sheetImageUrl`.
    Uploads use `FormData`; do **not** set a `Content-Type` header manually, the browser must
    set the multipart boundary itself.

`frontend/tests/client.test.ts` — Vitest, no DOM:

    starts with `/api/`.

    a readable sentence, and never produces the string "Something went wrong".
  Construct inputs with the global `Response` constructor — available in Node, so no jsdom.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser JS → FastAPI `/api/*` | Every value the artist types or picks leaves the browser here |
| server response → DOM | Project names, paths and error details from the API are rendered into the page |
| `location.hash` → view dispatch | A hash the artist can edit selects which view mounts and with which ids |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-XSS | Tampering | rendering project names, paths and `ApiError.detail` into the DOM | mitigate | All text is inserted with `textContent` / `document.createTextNode`, never `innerHTML` with interpolated values. This is the only injection surface in a framework-free hand-rolled view layer, and it is cheap to hold: a project name is artist-supplied and a path is filesystem-supplied, so neither is trusted markup. |
| T-01-HASH | Tampering | `parseRoute` | mitigate | `parseRoute` is total: an unknown, malformed or non-numeric hash falls back to the picker route rather than dispatching with a bad id, and ids are parsed with an explicit integer check. Covered by `frontend/tests/router.test.ts`. A bad id that does reach the API returns a 404 with neutral copy from plans 01-07/01-08. |
| T-01-ORIGIN | Information Disclosure | `apiUrl` | mitigate | Every request is a same-origin relative `/api/...` URL — grep-asserted that no absolute `http(s)://` appears in the client. In dev, Vite proxies to loopback; in production the SPA is served by the same FastAPI process. There is no configurable base URL to point at another host. |
| T-01-NOSAVE | Denial of Service | data loss on refresh | mitigate | There is no Save button and no client-side write buffer: every mutation fires on the action that produces it and the server commits synchronously (plan 01-03). On failure the artist's typed value stays visible and editable rather than being cleared, so a failed request cannot silently discard work. PROJ-05, UI-SPEC §7. |
| T-01-STORAGE | Information Disclosure | browser storage | mitigate | The picker keeps no `localStorage`/`sessionStorage` copy of project paths (grep-asserted). Recents come from the server index, which self-heals against a moved or deleted folder — D-04's rule that the index is never authoritative. |
| T-01-SC | Tampering | frontend dependencies | mitigate | This plan installs no new npm packages; the toolchain audited in plan 01-02 is unchanged, and the UI-SPEC's no-framework decision keeps the dependency tree at three audited dev packages. |
</threat_model>
