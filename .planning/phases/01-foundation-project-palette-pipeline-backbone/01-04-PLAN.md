<objective>
Build two of the phase's three foundation primitives: the declarative pipeline stage
registry, and the label-map exclusivity/exhaustiveness invariant check.

Neither has a real consumer in Phase 1. That is deliberate and is the reason the ROADMAP
put this phase first — "retrofitting them after an editor exists is far costlier than
building them first". Phase 2's panel editor, Phase 3's zone editor, Phase 5's snapper and
Phase 7's exporter all attach to the seams built here.

Purpose:
- D-10/D-11: declare the full chain (import -> panels -> protected -> zones -> propose ->
  snap -> review -> export) with dependencies and gates now, so later phases fill in
  runners against a contract that already exists instead of inventing one each time. Only
  `import` gets a runner this phase.
- RESEARCH.md Pattern 7: `masks.py` already implements exhaustiveness checking. What is
  missing is a loudly-failing assertion wrapper that Phase 3's zone editor can call after
  every merge/split/undo without re-deriving the report-parsing logic.

Output: `src/comiccolor/pipeline/` (stages + runner), `assert_invariant` and
`LabelMapInvariantError` in `masks.py`, and green tests for both.

**Explicitly not built:** the `PanelStageRun` per-panel run-tracking table that
`.planning/research/ARCHITECTURE.md` proposed. D-07 locked stage tracking to a single
`page.stage` value, and RESEARCH.md Pattern 5 supersedes the heavier design for this phase.
Building it now would be premature scope no requirement asks for.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| router → `run_stage` | A stage name arriving from an HTTP request reaches the registry lookup |
| edit surface → `assert_invariant` | Phase 3's zone editor will hand client-influenced label maps to the invariant check |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-STAGE | Elevation of Privilege | `pipeline/runner.py:run_stage` | mitigate | `run_stage` only ever dispatches to a runner declared in `STAGES`; an unknown name raises `KeyError` from `stage_for` and a declared-but-unimplemented stage raises `StageNotImplementedError`. There is no dynamic import, no `getattr` dispatch and no string-to-callable resolution, so a request cannot name arbitrary code to execute. Pinned by `test_run_stage_refuses_a_stage_with_no_runner` and `test_stage_lookup_by_name`. |
| T-01-GATE | Tampering | stage advancement | mitigate | `run_stage` never walks the chain, never runs upstream stages implicitly and never advances a page past its gate — D-06's forward-only-with-confirmation model relies on that, and `test_the_registry_never_advances_a_page_on_its_own` asserts it. |
| T-01-INV | Tampering | `masks.py:assert_invariant` | mitigate | Enforcement is fail-loud: a non-exhaustive map or a label leaked onto a line/protected pixel raises rather than returning a report a caller can ignore. Exclusivity is structurally unrepresentable (one int32 array), so there is no state for an attacker or a buggy undo to corrupt into overlap. |
| T-01-SQLI | Tampering | `runner.py` calling `Store` | transfer | The runner constructs no SQL; it calls `Store.set_page_stage`, whose parameterization is mitigated and tested in plan 01-03 (`T-01-SQLI`). |
</threat_model>
