<objective>
Implement the palette surface: PAL-01 (swatch upload creates named entries), PAL-03
(create, rename, recolour and delete by hand) and PAL-04 (recolour propagates with no
pipeline re-run).

Purpose: PAL-04's server side is **already built and already passing tests today** —
`store.update_palette_rgb()` bumps the entry and the project palette revision and touches no
region row, and `store.panels_affected_by()` returns the repaint set. CONTEXT.md is explicit
that "what's missing is the render/repaint path, not the data mechanic". This plan's job for
PAL-04 is therefore pure HTTP marshalling: call those two methods, return the affected page
count, and add nothing else. Reimplementing the propagation logic in the web layer would be
the failure mode here, not a thoroughness win.

D-09 is the constraint that shapes the whole router: palette edits sit entirely outside the
stage chain. Recolouring an entry is never a stage regression at any stage, including on a
fully reviewed page — no warning, no confirmation dialog, no re-run. That is
`flatting-pipeline-spec.md` §213 and it must be visible as an assertion, not just an absence.

Output: a complete `web/routers/palette.py` and three filled tests in
`tests/test_web/test_palette_routes.py`. The remaining four stubs in that file belong to
plan 01-10 (character sheets).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser multipart → Pillow decode | An artist-supplied swatch image reaches image decoding and CPU-bound extraction |
| browser JSON → palette mutations | RGB values, labels and entry ids arrive from the client and mutate the only place colour lives |
| browser multipart → filesystem | The swatch image itself is written into the project folder |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-IMG | Denial of Service | `POST /api/palette/swatch` | mitigate | Bytes go through `uploads.decode_image` (`Image.open().verify()` in a try/except, plus size, format and dimension bounds) before `extract_palette` runs, and `EmptyImageError` is mapped to 400 by the app-level handler from plan 01-06. Extraction itself runs at a fixed `K_MAX` regardless of input size, so there is no input-controlled loop bound. RESEARCH.md Pitfall 4. Asserted by the `bad` case in Task 2's verify and by the all-black criterion. |
| T-01-PATH | Tampering | swatch image write under `references/` | mitigate | The on-disk name is server-generated by `uploads.save_upload` from a UUID plus the format Pillow reported; the client filename never becomes a path component, and the module contains no `open(` of its own (grep-asserted). RESEARCH.md Pitfall 3, ASVS L1 V12. |
| T-01-RGB | Tampering | `PATCH /api/palette/{entry_id}` | mitigate | RGB channels are Pydantic-constrained to `0..255` and labels are length-bounded, so an out-of-range or oversized value is a 422 before the handler runs (ASVS L1 V5). The write goes only to `palette_entry` — the router contains no raw SQL (grep-asserted) and CLAUDE.md's "regions store `palette_entry_id`, never RGB" stays enforced by the schema, with `test_deleting_a_colour_leaves_its_regions_unpainted_not_wrong` checking it at the HTTP layer. |
| T-01-STAGE | Tampering | recolour vs. the stage chain | mitigate | D-09 requires that a palette edit never moves a page's stage. Enforced structurally: the module imports nothing from `comiccolor.pipeline` and contains no `set_page_stage`, `run_stage`, `invalidate` or re-run reference (grep-asserted), and `test_recolour_reports_affected_pages_and_leaves_stage_alone` asserts the stage is unchanged after a recolour. |
| T-01-IDOR | Elevation of Privilege | entry ids from the client | accept | One artist, one open project; ASVS V4 access control is out of scope per RESEARCH.md § Security Domain. An id outside the current project returns 404 with neutral copy, which is correctness rather than authorization. |
| T-01-SQLI | Tampering | routes calling `Store` | transfer | No SQL is constructed here (grep-asserted: no `SELECT`/`INSERT`/`UPDATE` literals). All access is through `model/store.py`, parameterization mitigated in plan 01-03. |
</threat_model>
