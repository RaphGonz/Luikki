<objective>
Implement the character-sheet reference flow: PROJ-03 ("upload character sheet images as
colour references") and PAL-02 ("have the app propose palette entries from an uploaded
character sheet and accept or reject each proposal individually").

Purpose: D-05 is that a reference image binds to a character at **accept** time, not upload
time. Uploading is one drag-and-drop with no prompts; the app asks for the character name
only when the artist is looking at the extracted colours and knows what to call them. That is
what lets entries land as `Kaito / hair / base` — the spec's label shape — without taxing
every upload with a form.

Output: a complete `web/routers/reference.py` and the four remaining tests in
`tests/test_web/test_palette_routes.py`.

**Two binding resolutions to build to, not re-open:**
1. **Not-yet-accepted sheets are filesystem-only** (user resolution of RESEARCH.md Open
   Question 2, 2026-08-10). They live at `<project>/references/pending/<uuid>.<ext>`; a
   database row is created only at accept time. Do **not** add a `reference_image` table this
   phase.
2. **Proposals are never persisted before accept.** They exist only in the HTTP response.
   RESEARCH.md § Anti-Patterns names persisting them as the mistake: it would need a proposal
   table and cleanup logic for rejected proposals, for no requirement that asks for it, and it
   would contradict D-06's gate philosophy generalised to palette proposals — nothing is real
   until confirmed.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser multipart → filesystem | Artist-supplied character sheets are written into the project folder |
| browser path parameter → filesystem | `sheet_id` from the URL selects which file is read, moved or deleted — the only client value in this module that influences a path |
| browser JSON → database | `character_name`, `part` and proposal indices create entity and palette rows |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-SHEETID | Tampering | `sheet_id` path parameter on every `/sheets/{sheet_id}/*` route | mitigate | `_validate_sheet_id` requires an exact 32-lowercase-hex match (`SHEET_ID_RE`) and runs **before** any path is constructed, so `../`, `..%2F`, absolute paths and separators are rejected as 404 with neutral copy. `_pending_path` additionally resolves the candidate and asserts containment inside the pending directory. Proven by `test_sheet_id_with_path_separators_is_rejected`, which also asserts `project.db` survives. ASVS L1 V12, RESEARCH.md § Security Domain. |
| T-01-PATH | Tampering | sheet upload and the accept-time move | mitigate | The on-disk name is server-generated by `uploads.save_upload` (UUID plus the format Pillow reported); the client filename is never a path component. The accept-time move composes both source and destination from `appconfig` constants plus the validated id, never from request data. RESEARCH.md Pitfall 3. |
| T-01-IMG | Denial of Service | `POST /api/references/sheets` and the accept-time re-derivation | mitigate | Bytes go through `uploads.decode_image` before extraction; `EmptyImageError` on an all-ink or all-paper sheet maps to 400 through the app-level handler from plan 01-06. Re-derivation on accept reads a file the server itself wrote and already validated. RESEARCH.md Pitfall 4. |
| T-01-EPHEM | Tampering | proposal indices in `SheetAcceptRequest` | mitigate | Proposals are re-derived server-side from the stored file; the client supplies only an integer index into that list, never an RGB value, so a client cannot inject an arbitrary colour under a character's name.
