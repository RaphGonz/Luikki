<objective>
Build the page surfaces: the volume's page grid with drag-and-drop upload, the page detail
screen, and the eight-segment pipeline stage strip that both use.

This is PROJ-02 ("upload line art pages and add more over time") and PROJ-04 ("see each page's
stage in the pipeline and open any page for editing") as the artist actually experiences them.

Purpose: the stage strip is the visible face of the registry built in plan 01-04, and
01-UI-SPEC.md §1 declares its full state machine now — including the two Phase 2+ states — so
that Phase 2 reuses the same component without redesigning it. It also imposes a rule that
matters more than it looks: the two "not yet reached" variants must render **identically** in
Phase 1, even though `GET /api/pipeline/stages` truthfully reports `has_runner`. The artist
should never see an internal "not implemented" distinction.

Output: `pageGrid.ts`, `pageDetail.ts`, `stageStrip.ts`, `uploadDrop.ts`, `pages.css` and two
Vitest suites over the pure models.

**Deliberately not built:** the Go-Back flow (D-08). 01-UI-SPEC.md §3 is explicit that the
confirmation dialog's cost sentence must be computed from real data at the moment it opens,
and that if the affected-count cannot yet be computed — which is true in Phase 1, where only
Import exists — the dialog is simply not reachable, and a vague sentence must never ship in its
place. So Phase 1 renders no Go-Back entry point at all. The contract is recorded in
01-UI-SPEC.md §3 and the `upstream` links needed to compute the sentence already exist in
`pipeline/stages.py`; Phase 2 implements it without re-deriving either.
</objective>

`segmentStates(stages: StageDto[], currentStage: string): SegmentModel[]` — a **pure** function,
no DOM, no fetch. For each stage in declaration order it returns
`{name, displayName, state, tooltip}` where `state` is:
  - `"complete"` for every stage strictly before `currentStage` in the declared order,
  - `"current"` for `currentStage` itself,
  - `"not-reached"` for everything after.
`tooltip` is `"Available in a later phase"` for `not-reached` segments and empty otherwise —
the Copywriting Contract's exact string.

`has_runner` is deliberately **not** consulted. 01-UI-SPEC.md §1 declares two distinct
not-yet-reached situations ("reachable in a future phase" and "no runner exists this phase")
and requires them to render identically, because the artist should never see an internal
not-implemented state. The API reports the distinction truthfully; this function is where the
product decision to ignore it lives, and that must be stated in the function docstring so a
later contributor does not "fix" it into a disabled-looking segment.

`renderStageStrip(mount: HTMLElement, model: SegmentModel[], variant: "compact" | "full")` —
builds the DOM. `compact` is a 4px-tall segmented bar with no labels, for the page grid;
`full` is 24px tall with Label-typography names beneath each segment, for the page detail
toolbar. Segments are non-interactive in Phase 1: no click handlers, no focusable elements
except the tooltip-bearing `title`/`aria-describedby`, because no stage past Import is
reachable. Give the strip `role="list"` with `aria-label="Pipeline stages"` and each segment
`role="listitem"` with an accessible name of `"{display name}: {state}"` so the state is not
conveyed by colour alone.

Add the strip's rules to `frontend/src/styles/pages.css`, referencing tokens only:
`--color-accent` for complete fill and the current outline, `--color-border` for not-reached
fill, `--color-text-primary` / `--color-text-muted` for the two label states, `--font-size-label`
and `--letter-spacing-label` for the names.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local files → browser → multipart POST | Artist-selected image files leave the machine's filesystem through the browser's file picker or drop event |
| server response → DOM | Page names, error details and stage metadata are rendered into the page |
| `pageId` / `volumeId` from the hash → API | Route ids selected by the artist reach `/api/pages` and `/api/volumes` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-XSS | Tampering | rendering `original_name` and upload failure `detail` | mitigate | All artist- and server-supplied text is inserted with `textContent`, never `innerHTML` — grep-asserted to be absent from both `pageGrid.ts` and `uploadDrop.ts`. `original_name` is artist-controlled (it comes from their own filename) so it is treated as text, never markup. The `alt` attribute is set as a property, not interpolated into a markup string. |
| T-01-SRC | Tampering | thumbnail `<img src>` | mitigate | `src` is the server-built `image_url` (`/api/pages/{id}/image`) carried on `PageResponse`; the frontend never composes a filesystem path or a path segment from a filename. The backend's own containment assertion (plan 01-08, T-01-SERVE) is the enforcement point. |
| T-01-UPLOAD | Denial of Service | drag-and-drop of very large or numerous files | mitigate | The `accept="image/*"` hint plus the server's `MAX_UPLOAD_BYTES` and format/dimension checks (plan 01-06) bound what can be processed; an oversized or unreadable file returns a per-file rejection rather than failing the batch or the process. Client-side validation is a courtesy — the server-side check is the control. |
| T-01-PARTIAL | Denial of Service | data loss on a mixed-batch upload | mitigate | `partitionUploadResult` keeps accepted pages and failures separate, and the view appends the accepted ones before rendering the failure banner, so a bad file never discards good uploads. Covered by `frontend/tests/uploadDrop.test.ts`'s mixed-batch case. UI-SPEC §7. |
| T-01-STAGEUI | Information Disclosure | stage strip rendering | mitigate | `segmentStates` ignores `has_runner` by design, so the UI cannot leak which stages are internally unimplemented — UI-SPEC §1's requirement, asserted by the identical-model test and by a grep for `has_runner` outside the explaining docstring. |
| T-01-GOBACK | Tampering | absent Go-Back flow | accept | No destructive stage-reset path exists in Phase 1, so there is nothing to guard. The risk being accepted is only that Phase 2 must implement UI-SPEC §3 correctly; the contract and the `upstream` links it needs are both already written down, and this plan records the omission in the source. |
</threat_model>
