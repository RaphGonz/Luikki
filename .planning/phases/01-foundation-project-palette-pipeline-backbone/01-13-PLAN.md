<objective>
Build the palette screen: swatch upload and its extraction result, hand create/rename/recolour/
delete, the recolour toast, and the character-sheet proposal review — all on one view.

This closes PAL-01, PAL-02, PAL-03 and PAL-04's user-facing half.

Purpose: 01-UI-SPEC.md §4 is emphatic that there is no separate "review extraction" screen
distinct from "the palette" — they are the same view, because D-15 accepts that adaptive
extraction sometimes returns the wrong count and makes PAL-03's manual add and delete the
recovery path. That path only works if it is reachable *from the extraction result*, not buried
elsewhere. §5 layers the character-sheet proposals onto the same screen as visually distinct
dashed cards.

D-09 shapes the recolour interaction as much as it shapes the router: recolouring is never a
stage regression, so it gets a toast and nothing else — no confirmation, no dialog, no
stage-strip change. CONTEXT.md notes the server side of PAL-04 was already built before this
phase started; this plan is the repaint path that was actually missing.

Output: `palette.ts`, `swatchCard.ts`, `proposalCard.ts`, `palette.css` and two Vitest suites
over the pure models.
</objective>

`entryLabel(character: string, part: string): string` — pure, returns `"{character} / {part}"`
with both sides trimmed. This mirrors the server's own `_entry_label` from plan 01-10; keeping a
client copy is for optimistic display only, and the server's value is authoritative — say so in
the docstring so the two do not silently diverge.

`acceptPayload(selection: ProposalSelection): SheetAcceptRequest` — pure, mapping the selected
proposal indices plus their per-entry parts and the shared character name into the request body.
It drops unselected proposals entirely (that is what rejection *is* when nothing was persisted),
trims inputs, and throws a typed error when the character name is empty or any selected entry
has no part, so the view can render an inline message rather than sending an invalid request.

`renderProposalCard(mount, proposal, handlers)` — a card the same 120x120 size as a swatch card
but with a **dashed** border in `--color-border`, so it reads as provisional at a glance
(UI-SPEC §5). It carries a multi-select checkbox, an accent Accept control with
`aria-label="Accept proposal"`, and a destructive Reject control with
`aria-label="Reject proposal"`. Reject removes the card from the DOM immediately with **no
confirmation dialog** — proposals are not real data, discarding one is cheap, and re-uploading
the sheet reproduces them. Explicitly do not wire the §3 destructive-dialog pattern here.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local files → browser → multipart POST | Artist-selected swatch and character-sheet images leave the filesystem through the browser |
| browser JSON → palette mutations | RGB values, labels, character names and parts reach the only place colour lives |
| server response → DOM | Palette labels, character names and error details are rendered into the page |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-XSS | Tampering | rendering palette labels, character names and `ApiError.detail` | mitigate | All text is inserted with `textContent`; `innerHTML` is grep-asserted absent from `palette.ts`, `swatchCard.ts` and `proposalCard.ts`. Labels and character names are artist-supplied free text and are treated as text, never markup — this is the main injection surface on a hand-rolled view layer with an inline-editable field. |
| T-01-INPUT | Tampering | `acceptPayload` and the recolour/rename calls | mitigate | `acceptPayload` validates client-side (non-empty character name, a part per selected entry, only selected indices) and emits exactly the `SheetAcceptRequest` shape, so malformed requests are caught before they leave. The authoritative check remains server-side: Pydantic constraints on RGB range and label length (plan 01-06) and the out-of-range-index 400 (plan 01-10). Client validation is ergonomics, not the control. |
| T-01-IMG | Denial of Service | swatch and sheet drop zones | transfer | Image decoding, size, format and dimension bounds are all enforced server-side in `web/uploads.py` (plans 01-06, 01-09, 01-10); the client only sets an `accept="image/*"` hint. A malformed image returns the UI-SPEC error sentence as a 400 and is rendered inline, never crashing the view. |
| T-01-EPHEM | Tampering | proposal indices | mitigate | The client sends indices, never RGB values, so it cannot inject an arbitrary colour under a character's name — the server re-derives the proposals from the stored file (plan 01-10, T-01-EPHEM). `acceptPayload` is grep- and test-asserted to emit no extra keys. |
| T-01-STAGE | Tampering | recolour interaction | mitigate | D-09 requires a palette edit to be a non-event for the pipeline. Enforced structurally on this screen: `grep -ci "stage"` over `palette.ts` and `swatchCard.ts` returns 0, and the recolour path contains no confirmation or dialog construction. The screen literally cannot move a stage because it never references one. |
| T-01-FLOOD | Denial of Service | colour picker drag | mitigate | The picker updates the swatch locally on `input` but only issues a write on `change`/blur (UI-SPEC §6, grep-asserted), so a drag across the colour wheel produces one request rather than hundreds against a synchronously-committing SQLite database. |
| T-01-DESTRUCT | Tampering | delete controls | mitigate | Deleting a palette entry — which is real, persisted data — gets the standing destructive confirmation shape from UI-SPEC §3 (named heading, concrete confirm verb, explicit cancel). Rejecting a proposal — which is not persisted at all — deliberately gets none. The asymmetry is the design: the ceremony is proportional to the cost. |
</threat_model>
