<objective>
Give panels a polygon (D-17), stop the solidity floor from throwing borderless panels away
(D-18), and build the one function that turns stored page-space protected polygons into the
boolean array the segmenter already knows how to exclude (D-21).

Purpose: PAN-01 needs polygons, not boxes, and the whole of PROT-04's mechanism is
`Segmenter.segment(line_mask, protected=...)` returning those pixels as label 0 — which is
already true. The missing piece is the page→panel clip, and the proof that it holds when a
bubble straddles a gutter, which is the exact case success criterion 4 names.

Output: two pure-function additions in `segmentation/`, and the first automated evidence for
success criterion 4.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-2-01 | Denial of Service | `rasterize_protected_for_panel` → `cv2.fillPoly` | mitigate | The destination array is allocated from the PANEL's dimensions, never from the polygon's extent, so a vertex at (10^9, 10^9) cannot influence allocation size; `cv2.fillPoly` clips to the destination bounds. Coordinate range is additionally bounded at the HTTP boundary in plan 02-05. |
| T-2-03 | Denial of Service | `rasterize_protected_for_panel` with degenerate input | mitigate | Polygons with fewer than 3 vertices are skipped, not passed to OpenCV; an empty list returns an all-False array of the panel's shape |
| T-2-12 | Tampering | Lowered `min_solidity` floor | accept | D-18 is an explicit user instruction to over-propose; a false panel proposal is corrected by the artist's one-click delete (D-19), and the confirmation gate in 02-11 refuses to advance a page with zero panels |
| T-2-13 | Tampering | `PanelParams.reading` default change | accept | Reading order is a display ordering, not an access-control or integrity property; both directions remain reachable and are covered by existing tests |
</threat_model>
