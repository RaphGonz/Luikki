<objective>
Build the hand-rolled canvas D-26 chose over Konva: one mount, two geometry layers, pointer
interaction for select/drag/insert/delete/draw, and pan/zoom — all of it expressed through
`transform.ts` so that "corrections hold at every zoom level" is true by construction rather than
by testing alone.

Purpose: D-26 rejected a HIGH-confidence library recommendation on one specific ground — Konva's
own stage scale/position model would fork `transform.ts`, the transform Phase 1 built and
unit-tested at 64x and 0.05x precisely because success criterion 2 is stated in terms of it. That
tradeoff only pays if this module actually delegates all coordinate math.

Output: the render and interaction layer. All of its *decisions* already live in plan 02-06's pure
modules; this file is the part that cannot be unit-tested for pixels and therefore must contain as
little logic as possible.

Implements D-26 (hand-rolled, zero runtime dependency, one coordinate authority) and D-19
(delete is instant, undo is the safety net — this module raises the events, the view commits them).
</objective>

  <action>
    Use Pointer Events (`pointerdown`, `pointermove`, `pointerup`, `pointercancel`) rather than
    mouse events, with `setPointerCapture` on the canvas during a drag, so stylus and mouse behave
    identically — 02-RESEARCH.md recommends this explicitly and a stylus-using colourist is the
    literal target user.

    Select tool:
    - `pointerdown` runs `hitTestVertex` first, then `hitTestEdge`, then `hitTestShape`, in that
      order, so a vertex always wins over the edge it sits on.
    - A vertex hit starts a drag: record `from` (the vertex's page-space position before the drag),
      capture the pointer.
    - `pointermove` during a drag calls `polygonState.moveVertex` and schedules a redraw. It
      performs no fetch and calls no `onCommit*` callback. A comment must name T-01-FLOOD and
      `swatchCard.ts`'s `input`-updates-visual / `change`-commits split as the precedent.
    - `pointerup` ends the drag and fires `onCommitVertexMove(shapeId, vertexIndex, point, from)`
      exactly once — and skips the call entirely when the vertex's final page-space position equals
      `from`, mirroring `swatchCard.ts`'s `lastCommittedHex` no-op guard so a click that did not
      move anything writes nothing.
    - An edge hit with no vertex hit calls `polygonState.insertVertex` and fires
      `onCommitPolygon(shapeId, newPolygon)` immediately — an insert has no drag phase.
    - `pointermove` with no drag in progress updates the hovered-edge ghost and redraws.
    - A shape hit with neither calls `selectShape` and fires `onSelectionChange`.
    - Clicking empty canvas clears the selection.

    Keyboard, bound on the mount element with `tabindex="0"` so focus is real and the handler is
    removable in `destroy()`:
    - `Delete`/`Backspace` with a vertex selected calls `polygonState.deleteVertex`; on
      `refused: true` it fires `onDeleteRefused()` and changes nothing, which is what produces the
      "A panel needs at least 3 points." toast in the view; otherwise it fires `onCommitPolygon`.
    - `Delete`/`Backspace` with a shape but no vertex selected fires `onCommitDelete(shapeId)`
      with no dialog and no intermediate confirmation, per D-19/§5.
    - `Escape` cancels an in-progress draft; `Enter` closes it.
    - `+`, `-` and `0` map to `zoomIn`, `zoomOut` and `fitToScreen` (UI-SPEC §9).

    Draw tool:
    - `pointerdown` appends a draft point; the draft's live edge follows the cursor on
      `pointermove`.
    - A `pointerdown` within `isWithinSnapClose` of the first draft vertex, or `Enter`, closes the
      draft: `closeDraft` returns the polygon and `onCommitDraw(polygon, drawKind)` fires once.
      A draft with fewer than 3 points does not close and does not commit.
    - `Escape` cancels without committing anything.

    Read-only mode: when `setReadOnly(mode, true)` has been called for the active layer, all
    mutating pointer and keyboard paths become no-ops while selection and hover still work. This
    is what a confirmed gate produces — UI-SPEC §4 makes panel polygons read-only in the Panels
    layer once the Panels gate is confirmed, and editing again requires Go-Back.

    Inactive-layer shapes are never hit-tested. A comment must say why: UI-SPEC's 40% dimming is
    described as "for spatial context only, non-interactive", so passing them to `hitTest` would
    let a click land on a shape the artist cannot see well and is not editing.

    `destroy()` removes every listener it added and cancels any pending animation frame.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-2-28 | Denial of Service | A write per `pointermove` flooding the panel/protected routes | mitigate | `onCommit*` is never called from a `pointermove` handler (asserted by grep and by a call-count test); the drag mutates local state and schedules a redraw only, and a zero-distance drag commits nothing at all, mirroring `swatchCard.ts`'s no-op guard |
| T-2-09 | Tampering (XSS) | Text drawn or inserted into the DOM | mitigate | Badge numerals are drawn with `fillText` on the canvas, and every DOM label uses `textContent`; `innerHTML` is forbidden and asserted absent (Phase 1 T-01-XSS) |

| T-2-32 | Tampering | Editing geometry the artist believes is frozen | mitigate | `setReadOnly(mode, true)` makes every mutating path a no-op, which is what a confirmed gate produces; a jsdom test asserts a drag in read-only mode commits nothing. | T-2-33 | Denial of Service | Unbounded zoom producing an enormous transform | mitigate | The interactive zoom range is clamped to 0.1–16; `transform.ts` itself is correct beyond that, so the clamp is a usability bound rather than a correctness one |
