polygon state mutation, and the session undo stack. No DOM, no canvas, no fetch — exactly the

browser.

    Then create `frontend/src/editor/hitTest.ts`. Module docstring mirrors `transform.ts`'s
    closing convention — "Pure arithmetic only: no DOM access, no canvas, imports only from
    `../geometry/transform`" — and states the load-bearing rule: distances are compared in
    SCREEN space, by converting each candidate page-space vertex through `labelMapToScreen` and
    measuring against the raw pointer position. Never convert the pointer to page space and
    compare there: a fixed page-space radius would grow and shrink with zoom, which is exactly
    the "correction holds only at the zoom level it was made" failure success criterion 2 forbids.

    Exports:
    - `VERTEX_HIT_RADIUS_SCREEN = 16`, `EDGE_HOVER_RADIUS_SCREEN = 12`,
      `SNAP_CLOSE_RADIUS_SCREEN = 12` — each with a comment citing the UI-SPEC line that fixes it.
    - `interface PolygonShape { id: number; polygon: Point[] }`
    - `interface VertexHit { shapeId: number; vertexIndex: number; distance: number }`
    - `interface EdgeHit { shapeId: number; edgeIndex: number; point: Point; distance: number }`
    - `hitTestVertex(screenPoint: Point, shapes: PolygonShape[], vp: Viewport): VertexHit | null`
    - `hitTestEdge(screenPoint: Point, shapes: PolygonShape[], vp: Viewport): EdgeHit | null` —
      point-to-segment distance in screen space; `point` is the projection expressed back in
      page space via `screenToLabelMap`, because that is what gets POSTed as the inserted vertex.
    - `hitTestShape(screenPoint: Point, shapes: PolygonShape[], vp: Viewport): number | null` —
      converts the pointer once with `screenToLabelMap` and runs `pointInPolygon` in page space
      (an area test, unlike the radius tests, is scale-free and correct in page space); iterates
      the array in reverse so the last-drawn shape wins.
    - `pointInPolygon(point: Point, polygon: Point[]): boolean` — standard ray-casting, no
      dependencies.
    - `isWithinSnapClose(screenPoint: Point, firstVertex: Point, vp: Viewport): boolean`

    No default exports, no classes, no mutable module state.

  <behavior>
    - Pushing 21 operations leaves a stack of depth 20 holding operations 2 through 21 — the oldest is dropped, not the newest refused.
    - `popOp` on an empty stack returns `{ op: null }` and an unchanged stack.
    - `invert` maps each op kind to the API intent that undoes it: a `move-vertex` inverts to a move back to `from`; an `insert-vertex` inverts to a delete of that index; a `delete-vertex` inverts to an insert of the recorded point at that index; an `add-shape` inverts to a delete of that shape id; a `remove-shape` inverts to a create carrying the removed shape's last-known polygon and kind.
    - `clearStack` empties it.
    - Pushing and popping never mutates the passed-in stack object.
  </behavior>
  <action>
    Write `frontend/tests/editor/undoStack.test.ts` first, including the 21-push cap test and one
    `invert` assertion per op kind.

    Then create `frontend/src/editor/undoStack.ts`. Docstring states the scope boundary in
    plain words: Phase 3 formally owns undo/redo against the label-map invariant and this is
    explicitly not that; this exists only to make UI-SPEC §5's no-confirmation deletion feel
    safe. It also states the deliberate simplification: undo re-issues the inverse mutation as a
    fresh API call and is not guaranteed to restore the same row id, only the same visible
    geometry.

    Exports:
    - `export const UNDO_CAP = 20;`
    - `export type UndoOp = { kind: "move-vertex"; shapeId: number; vertexIndex: number; from: Point } | { kind: "insert-vertex"; shapeId: number; vertexIndex: number } | { kind: "delete-vertex"; shapeId: number; vertexIndex: number; point: Point } | { kind: "add-shape"; shapeId: number } | { kind: "remove-shape"; shape: Shape };`
    - `export type UndoIntent = { kind: "move-vertex"; shapeId: number; vertexIndex: number; point: Point } | { kind: "delete-vertex"; shapeId: number; vertexIndex: number } | { kind: "insert-vertex"; shapeId: number; vertexIndex: number; point: Point } | { kind: "delete-shape"; shapeId: number } | { kind: "create-shape"; shape: Shape };`
    - `export interface UndoStack { ops: readonly UndoOp[] }`
    - `createUndoStack()`, `pushOp(stack, op)`, `popOp(stack): { stack: UndoStack; op: UndoOp | null }`,
      `clearStack(stack)`, `invert(op): UndoIntent`, `stackDepth(stack): number`.

    No timers, no persistence, no `localStorage` — the stack is session state held by the view
    and dies with it, which is what "does not survive a page reload" means concretely (edits
    commit synchronously per PROJ-05, so a reload always shows the last committed state).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pointer input → editor state | Untrusted coordinate input drives state mutation, but no privilege is crossed: this is all client-side and every mutation is re-validated server-side |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-2-21 | Tampering | Client-side vertex bounds | transfer | The client is not a security boundary; `Polygon`/`PixelCoord` in `schemas.py` (plan 02-05) re-validate every vertex server-side. This module deliberately does not duplicate that check, so there is no second, drifting definition of "valid" |
| T-2-22 | Denial of Service | Unbounded undo stack growth over a long session | mitigate | `UNDO_CAP = 20` drops the oldest op on push; a test asserts depth never exceeds 20 |
| T-2-23 | Information Disclosure | Editor state persisted to browser storage | mitigate | No `localStorage`/`sessionStorage` use is permitted in these modules; an acceptance-criteria grep asserts their absence. Session-only is both the UI-SPEC §6 contract and the simplest privacy posture |
| T-2-24 | Denial of Service | Vertex drag committing an API write per `pointermove` | transfer | Mitigated in plan 02-10's `canvasEditor.ts`, which commits on `pointerup` only (T-01-FLOOD precedent). These pure modules perform no I/O at all, which is what makes that separation enforceable |
</threat_model>
