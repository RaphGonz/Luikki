<objective>
Build the screen: one route, one canvas mount, two tool modes, two gates. This is where the
detector's proposals become something an artist can correct, and where every string UI-SPEC fixed
actually appears.

Purpose: 02-CONTEXT.md calls the screen/gate structure "the highest-leverage part of the contract"
and UI-SPEC §1 decided it — Phases 3 to 5 reuse whatever this establishes. The single-screen choice
exists so the artist does not lose their zoom and pan position between two edits of the same
artwork, and so the page raster loads once.

Output: the artist-facing surface for PAN-01/02/03 and PROT-01/02/03.

Implements D-19 (delete is instant with undo as the safety net), D-24 (the persistent SFX helper
text is the honesty this deferral requires), D-26 (one canvas, one transform), and the discretion
calls UI-SPEC recorded on screen structure, reading-order exposure and undo scope.
</objective>

      carrying `from`.

      appropriate `insert-vertex` or `delete-vertex` op.
    - `onCommitDraw(polygon, kind)` → `api.panels.create(pageId, polygon)` or
      `api.protected.create(pageId, kind, polygon)`, pushing an `add-shape` op with the id from
      the response.
    - `onCommitDelete(shapeId)` → `remove` on the right namespace, pushing a `remove-shape` op
      carrying the shape's last-known geometry so the inverse can recreate it. No confirmation
      dialog anywhere on this path — a comment must cite D-19/§5 and state that adding one would
      contradict the decision and make the routine case slow.
    - `onDeleteRefused()` → show the toast "A panel needs at least 3 points." (auto-dismiss,
      non-blocking), using the existing toast component.

    After every panel mutation, feed the response's full `panels` array back through
    `handle.setShapes("panels", ...)` so reading-order badges renumber from the server's values.
    A comment must state that the client never renumbers locally.

    Undo: one `UndoStack` per tool mode. `Ctrl+Z`/`Cmd+Z` and the toolbar Undo button both call
    `popOp` and then perform the API call `invert` describes, refreshing shapes from the response.
    The button is muted when the stack is empty. Clear the stack on tool-mode switch and on gate
    confirm. Persist nothing. A comment records §6's deliberate simplification: the inverse is
    replayed as a fresh API call, so a recreated shape may carry a new row id — the visible
    geometry is restored, not the identity — and this is exactly what "do not pre-build Phase 3's
    history model" means in practice.

    Gates:
    - The Panels CTA reads "Confirm & Continue to Protected", is accent-coloured, and is disabled
      (muted, not destructive) whenever the panel list is empty, carrying a `title` tooltip of

    - Clicking it calls `api.pages.confirmStage(pageId)`, shows the "Detecting speech bubbles…"

      on success sets both layers read-only and offers a "Done" affordance returning the artist to
      the page grid — Zones is a different editor that does not exist yet.
    - Both CTAs are the only forward control in their action area; there is no reject control.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server strings → rendered DOM | Page names, detection messages and Go-Back sentences originate server-side and are displayed |
| artist gesture → destructive API call | A single keystroke can delete a panel or mask with no confirmation |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-2-09 | Tampering (XSS) | Page name, detection message and helper copy rendering | mitigate | Every string is set with `textContent`; `innerHTML` is forbidden and asserted absent (Phase 1 T-01-XSS, `swatchCard.ts` precedent) |
| T-2-29 | Repudiation | Panel or mask deleted with no confirmation | accept | D-19/UI-SPEC §5 make deletion routine by design; the session undo stack is the specified safety net and a dialog is explicitly forbidden. The Panels gate's zero-panel refusal (client tooltip plus server 409) is the backstop that matters |
| T-2-28 | Denial of Service | Write flooding from drag interaction | mitigate | Inherited from plan 02-10: commits fire on `pointerup` only, and a zero-distance drag commits nothing |
| T-2-39 | Tampering | Editing geometry after its gate is confirmed | mitigate | `handle.setReadOnly` is called on confirm so the client stops offering the gesture; server-side the geometry routes remain open by design and Go-Back is the sanctioned path back, which is why the read-only state is a UX guarantee and not a security control — stated in the code comment so it is not mistaken for one |
| T-2-23 | Information Disclosure | Session undo state persisted to browser storage | mitigate | No storage API is used; asserted by grep. The stack dies with the view, matching UI-SPEC §6 |
| T-2-40 | Denial of Service | Repeated gate confirms racing each other | mitigate | The CTA is disabled while a confirm is in flight and re-enabled from the response, so a double-click cannot issue two transitions |
</threat_model>
