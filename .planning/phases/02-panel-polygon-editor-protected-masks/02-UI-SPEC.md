# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase does not introduce a new design language — it extends `01-UI-SPEC.md`, which is the token and pattern source of truth for the whole app through Phase 7. Every token table below reproduces Phase 1's declared values verbatim (no re-derivation) and calls out only what Phase 2 *adds*: the two-mode canvas editor, its vertex-handle and mask-overlay visual vocabulary, and the first real exercise of Phase 1's confirmation-gate (§2) and Go-Back (§3) patterns. Where this document is silent, `01-UI-SPEC.md` governs.

**Governing constraint carried forward unchanged:** true-neutral chrome, accent and destructive reserved to explicit lists, no tinted surface near artwork. Phase 2 adds new *uses* of the existing accent/destructive hues (the polygon editor needs a "selected" and a "delete" affordance) but introduces **no new hue** — the protected-mask overlay, which might tempt a third colour, is specified below using the existing muted-neutral token instead.

**D-26 is binding on this document:** no Konva, no canvas library. Every handle, hover state, hit target and overlay described below is drawn and hit-tested by hand against `frontend/src/geometry/transform.ts`, which remains the single coordinate authority. Nothing here should be read as assuming a library's transformer/selection widget.

## Spacing Scale

Reused verbatim from `01-UI-SPEC.md` / `tokens.css` — do not redeclare with different values:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps |
| sm | 8px | Compact spacing, vertex handle diameter |
| md | 16px | Default element spacing, floating zoom-pill internal padding |
| lg | 24px | Reading-order numbering badge diameter, toolbar segment padding |
| xl | 32px | `--icon-hit`, matches Phase 1's icon-only hit-target exception |
| 2xl | 48px | unchanged |
| 3xl | 64px | unchanged |

**Phase 2 exceptions (new, additive to Phase 1's list):**

- **Vertex handle:** 8px (`--space-sm`) visible diameter, but a **16px invisible hit radius** centred on it — the visible dot stays small so dense polygons don't look cluttered, but the click/drag target is generous for mouse-and-stylus precision. This is a hit-testing rule against `transform.ts`, not a second visible size.
- **Edge-midpoint "add vertex" ghost:** 6px diameter, half-opacity accent, appears only on hover within 12px of a polygon edge (screen space) — smaller than a real handle so it never gets confused with one at a glance.
- **Reading-order numbering badge:** 24px (`--space-lg`) diameter circle — reuses the scale, sized to comfortably fit two-digit panel numbers.
- **Floating zoom-pill controls:** 32px (`--icon-hit`) square buttons, matching Phase 1's existing icon-only exception — this is a mouse/stylus tool, not touch.
- **Toolbar tool-mode segmented control:** 32px tall buttons, reusing `--icon-hit`.

## Color

Reused verbatim from `01-UI-SPEC.md` / `tokens.css`:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#1E1E1E` | Canvas surround, app background |
| Secondary (30%) | `#2B2B2B` | Toolbar, floating zoom-pill, dialogs |
| Accent (10%) | `#5B8DEF` | See reserved-for list — Phase 1's list plus the Phase 2 additions below |
| Destructive | `#D9534F` | Destructive actions — see reserved-for list |

Supporting neutrals (unchanged): Border/divider `#3D3D3D`, Text primary `#E8E8E8`, Text muted `#9A9A9A`.

**Accent reserved for — Phase 2 additions** (appended to Phase 1's list, which still stands unchanged):
- The **selected** polygon's outline and its vertex handles (panel or protected mask, whichever tool mode is active) — 2px outline, handles filled accent with a 1px `--color-surface-dominant` ring for contrast against artwork of any tone.
- The **active tool-mode** button in the toolbar's segmented control (Select/Edit vs Draw).
- The **edge-midpoint "add vertex" ghost** (at reduced opacity — see Spacing Scale — this is still accent, not a new hue, just a lower-alpha use of it).
- The **snap-to-close halo** shown when drawing a new polygon and the cursor is within snapping distance of the start vertex.
- The **reading-order numbering badge** fill (numeral text renders in `--color-surface-dominant` for contrast against the blue fill — not a new colour, a reuse of the existing dominant-surface token as foreground).

**Destructive reserved for — Phase 2 additions** (appended to Phase 1's list):
- The **delete panel** and **delete protected mask** controls (toolbar trash icon when an object is selected, and the `Delete`/`Backspace` keyboard affordance conceptually maps to the same colour when the icon is shown).
- "Go back to an earlier stage" and its confirming dialog button — unchanged mechanism, now actually reachable for the first time (Panels and Protected are the first two stages a Go-Back target can point at).

**Protected-mask overlay — deliberately not a new hue.** A bubble/SFX mask renders as a **diagonal hatch pattern in `--color-text-muted` at 25% opacity**, with a **dashed `--color-border` outline** when detector-proposed-and-untouched, or a **solid `--color-border` outline** once the artist has hand-drawn it or edited it (see the "touched" state note in the Protected Masks section below). This keeps the "never coloured" concept visually legible without introducing a third hue next to artwork the artist is trying to judge by eye — the governing constraint from Phase 1 applies with full force here, since these overlays sit directly on top of the line art.

**Inactive-layer dimming (new rule, both directions):** whichever geometry layer is *not* the active tool mode's subject — protected masks while in Panel tool mode, or panel polygons while in Protected tool mode — renders at **40% opacity, non-interactive**, for spatial context only. This has no dedicated token: it is a CSS `opacity` applied to the whole inactive layer group, not a colour change.

## Phase-Specific Interaction Contracts

CONTEXT.md names the screen/gate structure as "the highest-leverage part of the contract" — Phases 3–5 reuse whatever pattern this section establishes. Treat this whole section as load-bearing, equal in weight to the token tables above.

### 1. Screen and gate structure (Claude's discretion — decided)

**One screen, two sequential tool modes, two sequential confirmation gates.** Not two separate routed screens.

Rationale: Panels and Protected operate on the exact same page raster and the exact same coordinate transform (D-26); Protected masks are clipped per-panel only at *use* time (D-21), so the artist benefits from seeing panel geometry as context while placing bubble masks, and vice versa on Go-Back. Mounting one canvas component twice (once per route) would mean loading the page raster twice and re-deriving viewport/zoom state on navigation, for a screen pair that is conceptually "correct the geometry of this page" as a single continuous task. A route change here would also cost the artist their zoom/pan position between two edits of the same artwork — a real cost the single-screen model avoids for free.

Concretely:
- URL/route: one page-editor route per page (e.g. `/page/{id}/edit`), independent of which of the two stages is current.
- The toolbar's tool-mode segmented control, its kind-selector, and the primary CTA all key off `page.stage` (`"panels"` or `"protected"`), exactly as Phase 1's stage strip already keys its states off the same field.
- Confirming the Panels gate does **not** navigate away — it swaps the active layer (Panels → dimmed context, Protected → active with the bubble-detection loading state, then interactive) in place, on the same canvas mount.
- Confirming the Protected gate returns the artist to the page grid or page detail (their choice via a "Done" affordance — no v1 requirement forces staying), since Zones (Phase 3) is a different editor entirely and does not yet exist.

This is the pattern Phase 3 inherits for its own (single-stage) editor, and the pattern Phases 4–5 should consult before assuming a new route is the default answer.

### 2. Panel polygon editing (PAN-01, PAN-02, PAN-03)

- On entering Panels tool mode, the canvas shows the page raster full-bleed with detected panel polygons overlaid, each carrying its reading-order numbering badge (top-left of its bounding box).
- If polygons are not yet available when the screen opens (runner not yet executed for this page), show a full-canvas loading state: centred spinner, Body text "Detecting panels…" — this is the same shape as the bubble-detection loading state in §1's copy table, reused, not reinvented.
- **Select/Edit tool (default):** click a polygon to select it (accent outline + handles appear per the Color section). Drag a vertex handle to move it — the drag renders live, but **the API write commits only on `mouseup`**, never on every `mousemove` (T-01-FLOOD precedent from Phase 1's colour picker — do not flood the write path). Hover an edge to reveal the add-vertex ghost; click it to insert a real vertex at that point, committing immediately. Select a vertex and press `Delete`/`Backspace` to remove it, unless doing so would drop the polygon below 3 vertices — in that case the delete is refused and the toast in the Copywriting table appears.
- **Draw panel tool:** click to place vertices in sequence; a live edge preview follows the cursor. Close the polygon either by clicking within the snap-to-close halo of the first vertex, or by pressing `Enter`. `Escape` cancels the in-progress draw without committing anything.
- **Delete panel:** select a polygon, then either click the destructive trash icon that appears near its bounding box, or press `Delete`/`Backspace` with nothing else focused. **No confirmation dialog** — see §5.
- Numbering badges always reflect current reading order live as polygons are added/deleted/reordered by position — the artist never has to manually renumber.

### 3. Protected mask editing (PROT-01, PROT-02, PROT-03)

- Same interaction vocabulary as panels — move/add/delete vertex, draw-from-scratch, delete-whole-object — reused verbatim so the artist learns one editing model for the whole screen, per D-26's "the planner writes pan/zoom, handle rendering and z-ordering directly" (one shared implementation, two data sources).
- Detector-proposed masks (D-22/D-23) render immediately on entering Protected tool mode, styled per the Color section's hatch/dashed treatment, with **no accept/reject step** — this deliberately differs from Phase 1's character-sheet proposal flow (§5 of `01-UI-SPEC.md`). Rationale: D-19's "over-propose, let the artist delete" philosophy extends here; a bubble mask is either right, needs reshaping, or gets deleted — there is no intermediate "proposal you haven't looked at yet" state worth a separate accept gate, and PROT-01/03's wording ("proposes… reshape or delete") never describes an accept step.
- **"Touched" state (planner note):** a mask needs some way to flip from "detector-proposed, dashed outline" to "solid outline" the moment the artist reshapes it or draws a new one by hand — this is a client-visible boolean/enum the planner should add to the mask's data shape (exact field name/schema is a planning decision, not this document's).
- **Kind selector:** visible only while "Draw mask" is active, defaulting to "Bubble". Detector-proposed masks are always tagged "Bubble" by construction (D-24 — SFX gets no automatic proposal). Hand-drawn masks let the artist pick "Bubble" or "SFX" before or while drawing.
- A mask straddling two panels (D-20) renders as one continuous overlay; it is never visually split at a panel boundary in this editor — clipping is a use-time server concern (D-21), invisible here.
- The persistent helper text from the Copywriting table stays visible for the whole time Protected tool mode is active — not a one-time dismissible tip — so the artist is never left assuming SFX coverage is complete.

### 4. Confirmation gates (D-06, D-07 — extending `01-UI-SPEC.md` §2)

Both gates follow Phase 1's established shape exactly: a persistent action area with exactly one primary control, no reject control, confirming is the only forward action.

- **Panels gate — "Confirm & Continue to Protected".** Accent-coloured. **Disabled** (muted, not destructive) when the page currently has zero panels, with a tooltip reading the Copywriting table's empty-state body text. This is a new rule beyond Phase 1's generic gate description — Phase 1 never had a "the artist deleted everything" case since it had no delete-heavy surface; Phase 2 does (D-19), so the gate must guard against a page leaving this stage with nothing to segment later.
- **Protected gate — "Confirm & Continue to Zones".** Accent-coloured. **Never disabled by mask count** — a page legitimately having zero speech bubbles is valid (e.g. a splash page with no dialogue) and must not block progress.
- On confirming the Panels gate: `page.stage` transitions `panels → protected`; panel polygons become read-only in the Panels layer (edits require Go-Back); the bubble-detection runner executes, shown via the loading-state copy above; the screen swaps to Protected tool mode once it completes.
- On confirming the Protected gate: `page.stage` transitions `protected → zones`; protected masks become read-only; the artist returns to the page grid or page detail (Zones has no runner yet — Phase 1's stage-strip rule already renders it as the neutral "not yet reached" segment, unchanged).

### 5. Deletion is routine, not destructive-confirmed (D-19)

Explicit contrast with Go-Back, which stays a heavyweight modal: **deleting a panel polygon or a protected mask never opens a confirmation dialog.** This mirrors `01-UI-SPEC.md` §5's "Reject" pattern for character-sheet proposals — destructive-coloured, instant, no modal — extended here because CONTEXT.md is explicit that deletion "is a routine, high-frequency action here, not an exceptional one," precisely because D-18 deliberately over-proposes panels and expects the artist to prune them constantly. What makes this safe without a dialog is §6's in-editor undo, not a confirmation step — do not add a dialog "to be safe"; that would contradict D-19's explicit framing and make the routine case slow.

### 6. Minimal in-editor undo (Claude's discretion — decided, scoped narrowly)

Phase 3 formally owns undo/redo with a real history model against the label-map invariant; this is explicitly *not* that. Phase 2 needs only enough to make §5's no-confirmation deletion feel safe.

- **Undo only, no redo.** `Ctrl+Z`/`Cmd+Z`, plus a toolbar `Undo2` icon button (32px, muted when the stack is empty, `aria-label="Undo last edit"`).
- **Scope:** one stack per tool mode (Panels, Protected), holding the last **20** committed operations (vertex move, vertex add, vertex delete, polygon/mask draw, polygon/mask delete) in that mode's current session.
- **Mechanism:** undo replays the *inverse* of the last committed mutation as a fresh API call (re-issue the prior vertex position, re-POST a deleted geometry's last-known shape, DELETE a just-drawn object) — it is not guaranteed to restore the exact same row id, only the same visible geometry. This simplification is deliberate and is exactly what "do not pre-build Phase 3's history model" means in practice.
- **Cleared, not carried forward:** the stack resets when the artist switches tool mode (Panels ↔ Protected) or confirms a gate. It does not survive a page reload — edits still commit synchronously per PROJ-05 (no Save button anywhere), so a reload always reflects the last committed state; undo is a same-session convenience, not a persistence layer.

### 7. Reading order (Claude's discretion — decided, minimal exposure)

Reading order stays a **backend parameter passed to `_reading_order()`**, defaulting to left-to-right (the project's own motivating examples are Franco-Belgian, and `_gutter_network`/borderless-panel handling was raised unprompted in that context) — it is **not exposed as an editable per-project setting this phase**. The Panels toolbar shows a small, non-interactive readout — "Reading order: Left → Right" — so the convention is visible and never silently assumed, satisfying the same "don't imply more than is true" principle D-24 already established for SFX detection, without building a settings screen this phase does not otherwise need. If manga (right-to-left) support becomes a real near-term need, the natural extension is a per-project setting exposed from the project shell — not a per-page toggle in this editor.

### 8. Go-Back, now reachable for the first time (D-08 — extending `01-UI-SPEC.md` §3)

The component and copy contract from Phase 1 §3 is unchanged and is not re-derived here. What Phase 2 adds is the first two real, computable instances of its server-generated cost sentence:

- Going back from **Protected** to **Panels**: dialog heading "Go back to Panels?" — body example: *"This discards 4 protected masks and re-runs bubble detection for the whole page."* — confirm button "Go back and discard 4 edits".
- Going back from **Panels** to **Import**: dialog heading "Go back to Import?" — body example: *"This discards 6 panel polygons and 4 protected masks, and re-runs panel detection for the whole page."* — confirm button "Go back and discard 10 edits".
- As Phase 1 states: if the affected-count cannot yet be computed for a given transition, that Go-Back target is simply not offered in the target list — never a vague sentence with no numbers in it.
- Entry point placement on this screen: the toolbar's right-hand cluster, as a low-emphasis destructive-coloured text link, positioned before (visually subordinate to) the primary Confirm button — never a filled button, never competing with forward motion, per Phase 1's original rationale.

### 9. Zoom, pan and the coordinate-transform contract (success criterion 2)

- A floating control pill (secondary surface, 32px icon buttons, `ZoomIn`/`ZoomOut`/`Maximize`) sits bottom-right over the canvas, offset `--space-lg` (24px) from both edges — an overlay layer, not part of the base shell padding rules.
- Default view on entering either tool mode: **fit-to-screen**, computed from the page raster's dimensions and the available canvas area.
- Every vertex position, hit test, hover state and drag delta routes through `screenToLabelMap`/`labelMapToScreen` — no interaction in this editor computes screen-to-page math independently. This is what makes success criterion 2 ("corrections hold at every zoom level") true by construction rather than by testing alone.
- The zoom-pill's numeric range is a UI convenience, not a transform limitation — `transform.ts` is unit-tested at 64× and 0.05×; the pill need only expose a sensible interactive range (e.g. 10%–1600%) with `+`/`-`/`0` keyboard shortcuts, since no artist will manually type 6400%.

### 10. Layout and shell integration (extends `01-UI-SPEC.md` §8)

- Sidebar (240px) and the 56px toolbar strip are unchanged in dimension — Phase 1 built the toolbar height specifically so this phase would not need to reconcile a new header size.
- Toolbar contents while this editor is open, left to right: breadcrumb ("← Back to page grid" + page name, Body typography) — tool-mode segmented control + kind selector (when relevant) + Undo button — Go-Back text link — primary Confirm button.
- Main content area is full-bleed for the canvas, edge-to-edge, no card padding — exactly the constraint Phase 1's §8 reserved this region for.
- Z-order: canvas base (z0) → inactive-layer context at 40% opacity (z1) → active-layer overlays and handles (z2) → floating zoom pill (z10) → Go-Back confirmation modal (z100, secondary surface, centred — unchanged from Phase 1).

**Accessibility — icon-only controls (extends Phase 1's rule verbatim).** Every icon-only control this phase adds (`Trash2`, `Undo2`, `ZoomIn`, `ZoomOut`, `Maximize`, tool-mode buttons if rendered icon-only at narrow widths) MUST carry an `aria-label` naming its semantic action and target, per the Copywriting table above — never labelled by glyph.
